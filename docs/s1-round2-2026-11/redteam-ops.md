# Red team: operations and failure (S2, S3), round 2

Severity: H = ships a real loss or outage, M = degrades under plausible conditions, L = hygiene.

1. H, R2.2 time budget. Round-1 failure path is already 0.8 claim + 3.5 Klaviyo + 0.8 release = 5.1 s. A sequential IP hit (0.8) before the claim makes 5.9 s, and the success path adds up to 2.5 s subscribe on top of 0.8 + 0.8 + 3.5 = 7.6 s. Any Neon cold start (hit and claim each pay it) eats the rest of the 10 s, and the function is killed mid-Klaviyo with no release. netlify.toml sets no timeout. Change: run the IP hit inside the same `sql.transaction` array as the claim (one round trip, one 800 ms cap), or `Promise.all` both under a single shared 800 ms deadline. Never two serial caps. State the worst-case sum in the spec and test it with a fake slow DB.
2. H, R2.1 429 vs claim order. If the IP hit runs before classify, a `retry` (same eventId, lost response) burns a slot, and so does every 502 and every `repeat`. A flaky Klaviyo hour makes real families the 6th and 31st attempt. Change: count only requests classified `new`, or skip the count on `retry`; document that repeats and failed sign-ups do not count. If the hit must come first, decrement is not possible, so accept classify-first and put both in one transaction.
3. H, R2.1 identity of the client. Two traps. (a) No `x-nf-client-connection-ip` and no XFF yields an empty key: every such request shares one bucket and the 31st locks everyone out. Skip the check when no valid IP (`isIP`, as sendMetaLead does). (b) The XFF fallback is client-settable: on Netlify the nf header is always present, so the fallback is only reachable off-platform; but if it is used when nf is missing, a spoofed XFF both evades the cap and creates unbounded unique keys. Change: use XFF only when `process.env.NETLIFY` is unset, and say so.
4. M, R2.1 fixed window at the hour edge. `hit()` floors to the clock hour, so a client sends 5 quiet-free + 5 more across :59/:00 (10 clean Leads) and 30 + 30 before a 429. Fine for abuse, but R2.1 says "rolling or fixed": pick fixed, write the 2x edge as accepted, and test with an injected clock or by asserting the SQL window. Also `now()` is DB time, so tests cannot fake it: expose a window-start override or test via the SQL string only.
5. M, R2.1 shared IPs. School Wi-Fi, a library, carrier CGNAT, or a Season 01 class night put 6+ real families behind one IP; they get `quiet:true`, so Meta never sees their Leads and the ads optimizer under-counts exactly the busiest Seattle/Austin audiences. Change: log a `quiet` counter (hashed key prefix, no IP) so Jamie can see how often it fires; consider 8 per hour for the quiet line. Confirm with Jamie that silently dropping a real Lead is the intended trade.
6. M, rows growth and cleanup. `s1_rate_limits` now gets one row per IP-hour plus, already, two rows (em, ev) per sign-up held 24 h. Cleanup is only the 1% branch inside `hit()`/`hitPair`, and its `delete ... where window_start < now() - interval '1 day'` has no index on `window_start` (PK is key, window_start), so it is a sequential scan that runs on a request path. `classifySignup` never triggers cleanup. Also the 24 h claim reads use `key = any(...)`, which is fine. Change: add `create index on s1_rate_limits (window_start)` in a 0004 migration, cap cleanup with `limit` via a ctid subselect, and run it from the new IP hit path. Bound the flood: a bot rotating real IPs writes at most one row per IP-hour, but a bot rotating emails writes 2 rows per request until the IP hits 30 (then 429 writes only the counter): state that ceiling (about 60 rows per IP-hour).
7. H, R2.3 step lock when no claim exists. A step is dropped with `200 {ok:true}` and nothing written when there is no matching `s1wl:ev:` row. That row is missing in four legitimate cases: (a) DB down or over 800 ms at sign-up (classify fails open, `claimed` is empty, no row); (b) a sign-up whose claim committed after the cap and was later released or never written; (c) the sign-up classified `repeat` with an eventId the page then reuses (row exists, fine) versus no eventId (no ev key at all); (d) the visitor took longer than 24 h between sign-up and the step (text-karlin from a saved tab). Result: a family that gave a phone number to "Text our founder" is silently discarded, the page shows success, and nobody knows. Change: log a counter line `step dropped: no claim` (no email); on DB failure the step proceeds (already specified, but also for the case where the sign-up's own claim failed open: have the sign-up response return `claimed:false` is not allowed by R2.4, so instead let the page not gate on it and accept the loss for (a) knowingly); for text-karlin only, fall back to the `s1wl:em:` key (any sign-up of this email in 24 h) so a lost ev row does not lose a phone number.
8. M, R2.3 deploy skew and old clients. Tabs and the popup JS open before the deploy, and CDN-cached landing HTML, send steps without `eventId`; strict match drops every one of them for hours. Change: when the step has no eventId, match on the `em` key only; require the ev key only when an eventId is present. Say it in R2.3 so the test covers both.
9. M, R2.3 extra round trip. The step now waits on a claim read (up to 800 ms) before the Klaviyo call; the page awaits it. Cap shares the budget in item 1. Reads should be a single `select 1 ... limit 1`, not the full transaction with advisory lock.
10. H, R3.3 drift test going toothless. Today the test strips comment lines and compares route code, then deepEquals headers and bodies. The new delta has to cover: the `<meta robots>` line now hard-coded in `join-b.html`, the `x-robots-tag` header, canonical, description, JSON-LD. Do not regex-strip "everything between head tags". Change: (a) put the delta in one named arg (`indexable: boolean` or a `head` object) passed by each route, ideally both routes become one-line wrappers over a shared handler in `lib/season1/joinHandler.ts`, so the code compare is trivial; (b) wrap the SEO block in exact markers `<!--SEO:start-->` and `<!--SEO:end-->`, each required exactly once per rendered page and inside `<head>`; (c) compare bodies with only that span removed; (d) compare headers with only `x-robots-tag` removed, then assert it is absent on /join and `noindex` on /b; (e) assert positives: /join has canonical `https://ekuzo.gg/season1/join`, no `noindex`, JSON-LD parses; /b has `noindex` and canonical absent or pointing to /join. Mutation check: add one test that edits a price string outside the block and expects failure.
11. H, R3.2 previews and closed state get indexed. The route is the same on deploy previews, branch deploys, localhost and test mode. Indexable must require `mode === "live"` on the live host, else keep noindex (fail closed), and the canonical must be hard-coded to ekuzo.gg, never built from `host`. When `mode === "off"` or the commit window is closed, the page says "Signups are paused" while JSON-LD Offer would still say InStock: emit availability from `isOpen`, or drop Offer when closed, and decide whether a paused page should flip back to noindex. Query variants (`?src=`, `?ad=`) must canonicalise to the bare URL.
12. M, R3.2 JSON-LD in a raw template slot. `TAGS` and `URL_ALLOW` are RAW. JSON-LD must come from `lib/schema.ts` through the escaping `JsonLd` path (escape `<` and U+2028/9); a price or FAQ answer containing `</script>` or an apostrophe from canon must not break the block. Test with a hostile canon string.
13. M, Next caching. Both routes are `force-dynamic` with `private, no-store`, so there is no Next data cache or full-route cache to serve /b's head on /join: safe. Risks: (a) someone later adds `s-maxage` for speed: Netlify keys on path so /join and /b stay separate, but `?src=` renders `SIGNUP` differently, so the key must vary on the query (Netlify default does; confirm with `Cache-Status`); (b) every Googlebot crawl runs the function and `readFileSync`: fine, but if the SEO block moves to a separate file, add it to `outputFileTracingIncludes` or the function throws ENOENT in production only (nft tracks the existing literal `path.join(process.cwd(), ...)`; a second file read the same way is traced, a computed path is not). Add a post-deploy curl to the checklist for both heads.
14. M, R3.4 sitemap. `app/sitemap.ts` is a hand-kept static array; a route handler is not discovered, so the entry is manual and easy to forget or to add for the wrong URL. Its rule says `lastModified` is a real date, never `new Date()`: use the date the canon or template last changed, not the deploy date, and bump it with offer.ts changes (prices change the page). Add a test: sitemap contains `/season1/join` and none of `/season1`, `/season1/join/b`, `/season1/join/jersey`, `/season1/join/signup`; and that no sitemap URL's route emits noindex (use the same `indexable` flag). `public/robots.txt` has no season1 Disallow (good): add a test so none is added, since a disallow would block the canonical and noindex signals.
15. L, R3.4 llms.txt. It says ages 9 to 17 and mid January to May 2027; the template uses `AGE_MIN`/`AGE_MAX` and `lockInDate()`. Check against offer.ts and the canon, and add a unit test comparing the three, so the page, canon and llms.txt cannot drift.
16. L, R2.4 logging. The existing `console.error("KLAVIYO_PRIVATE_API_KEY not set ... lost:", email)` logs a raw email, against the new "no raw email in logs" test. Fix or exempt it explicitly; the test should scan every log call path with an email and IP fixture.
