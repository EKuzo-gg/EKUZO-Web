## S2 gaps

6. H R2.1 IP source. Spec says "else first x-forwarded-for". The first entry is attacker supplied; a bot rotates XFF and never hits a limit. Netlify sets `x-nf-client-connection-ip` itself, so trust only that. No valid header (dev, odd proxy): skip the limiter entirely. Do NOT bucket under "noip" like signup/route.ts:46 and crew/[code]/route.ts:75 do: one shared bucket would 429 every family at once.
7. H IPv6. Bot owners get a /64 (2^64 addresses), so per-address keys never trip. Change: normalize with `net` (lowercase, expand), key IPv4 as is and IPv6 as the /64 prefix; strip `::ffff:` mapping so v4 and mapped v4 share a key.
8. H Botnet and proxy farms pass 5 per IP forever. There is no global ceiling like the commit route has (M1). Scenario: 500 proxies x 5 = 2500 CAPI Leads in an hour that teach Meta to find bots. Change: a global key (`s1wl:glob:hour`); above N (suggest 3x the best ad hour seen, say 150) every sign-up goes quiet and one ops alert per hour fires. Quiet-by-default is the safe direction because it only costs attribution.
9. M NAT families. Mobile CGNAT (T-Mobile, Verizon home internet) and school or UT wifi put many real parents on one IP, and the ads run 7 to 8:30 pm when they cluster. 5 an hour is tight for a Community Night or a school flyer push. Cost of quiet is silent under-reporting of real Leads to Meta, which then optimizes on fewer signals. Change: count only class `new` (not repeat, not retry), raise quiet to 8 to 10, keep 30 for 429, and log a `quiet` counter by ad so Jamie can see if real families were hit.
10. M Count ordering. If hit() runs before classifySignup, a lost-response retry or a repeat burns the family's budget. Run classify first, hit only for `new`/`retry`... or one transaction.
11. M Fixed window (hit() floors the hour) allows 2x the limit across a boundary: 10 quiet-free signups in minutes. R2.1 says "rolling or fixed": pick fixed, accept it, state it in the test. If a real cap matters, use 10 minute buckets summed.
12. M Fail open needs its own timer. hit() has no cap, and a slow DB eats 800 ms twice. Race hit() with 800 ms; a late insert still counts, fine. Prefer folding the limiter into classifySignup's transaction (one round trip, one 800 ms). Also keyHash THROWS when S1_REF_SECRET is missing on a live key (rules.ts:624); classifySignup swallows that today, so dedupe silently off. Same would happen to S2. Change: warn once per cold start with a fixed string, and check in the deploy list that S1_REF_SECRET is set.
13. L `quiet:true` tells an attacker exactly where the threshold is, so a bot can sit at 5 an hour per IP indefinitely. Accept the leak (the flag is needed by the page), but make sure quiet never differs in latency or body shape from a normal sign-up beyond that field.
14. L No Origin check on /api/season-one (commit has isCrossSite). A cross-site `text/plain` form POST is parsed by req.json(). Add the same guard; bots ignore it, but browsers on a hostile page cannot be used as proxies.

## Quiet path teaching Meta

Landing (landing.html:1448-1452) fires fbq Lead, GA4 generate_lead, Clarity signup, and the popup (SeasonOnePopup.tsx:140, via lib/analytics.ts:122 trackLead) fires all three. Both must read `j.quiet===true` next to `repeat`, and the test must fail if any of the three fires. An old cached landing page (no quiet check) will still fire Lead for a quiet sign-up; the landing is served by route.ts so check its cache-control.
16. M Quiet sign-ups still reach the confirmation card and the join link, so Pixel ViewContent (tags.ts:77, join page) and later PageView from the same bot session still feed Meta. Change: only suppress what is cheap (the three events plus `localStorage ekuzo_s1_joined`); note the residual in the spec and accept it.
17. M A repeat is already treated as non-Lead; a bot alternating emails is `new` each time, so repeat logic gives no protection. Do not count on it.
18. L fbclid and `ad` are client supplied (route.ts:248-250, normalizeAd). A bot can attach a real ad click id or a different ad code and move credit between ads. Low value; note only.

## Step lock (R2.3)

19. H The claim is not exclusive to the first sign-up. classifySignup claims `s1wl:ev:` for the repeat path too (route.ts:163, keys not yet seen are all claimed). Scenario: a stranger POSTs a normal sign-up for victim@x with their own eventId within 24 h of the real one; it reads `repeat`, still claims their eventId, and that pair now unlocks `text-karlin` on the victim profile. Change: claim the ev key only for `new` (and `retry`), never for `repeat`; or store a kind and let steps require kind=new.
20. M Phone not bound to anything. Even with a valid pair, the parent can submit any phone (Karlin texts a stranger). Cap one text-karlin per claim, reject when phone differs from an earlier one, and consider requiring the page to send it within 30 minutes of the claim.
21. M "No match: 200 {ok:true}" breaks the landing's own retry. If the claim was released (failed event) or timed out at 800 ms, a real family's age and games are dropped silently, and the page shows "sent". Games is the main metric for hero=games. Change: at least log a `step_dropped` count by reason (no PII) so Jamie sees the rate; the sign-up that created it must not release the claim on the Klaviyo 502 path without the client being told.
22. M Fail open on step lock reopens item 1 whenever the DB is slow; an attacker who can time out the DB (rate bursts) gets free steps. Accept, but bound with the per-email step cap in item 1 which needs no read of the claim.
23. L Popup sends `email.trim()` from state, not the email the eventId was minted for (SeasonOnePopup.tsx:160). If a family edits the field after submit the pair mismatches and the step drops. Send the submitted email.
