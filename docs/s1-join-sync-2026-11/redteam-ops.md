## W3 (24 h sign-up check)

1. **major, R3.1/R3.3/M1.** The repeat path cannot tell "already fully processed" from "partly processed". Scenario: first request writes the Klaviyo event (profile gets `season1_joined_at`), then the lambda hits Netlify's 10 s cap or Meta is down before the CAPI Lead. Client gets an error, retries with the same `eventId`. Server sees the property, returns `repeat:true`, skips CAPI; the client (R3.4) fires no Pixel Lead. Zero Leads reach Meta. Fix: write `season1_last_event_id` on the profile with the event. On lookup, if it equals the request's sanitized `eventId`, treat it as a retry of the same attempt: skip the Klaviyo event, still send CAPI Lead (Meta dedupes on `event_id`), return `{ok:true}` (not `repeat`) so the client fires its Pixel Lead with the same id. Add as R3.1b plus a test.

2. **major, R3.1/R3.3.** Eventual consistency is not covered by R3.3. `POST /api/events` returns 202; profile properties are applied asynchronously (usually seconds, occasionally longer under load). Lookups inside that gap see no property and proceed as new. R3.3 only helps when the retry carries the same `eventId`. A page reload (the `eventId` is in memory only), or a second tap on a new page load within seconds, makes a new `eventId` and a new `unique_id`, so two events and two Leads. Fix: state in the spec that the check is best-effort within a window of a few seconds to minutes after a write, and that H2 must wait at least 60 s between the two sign-ups or it tests the wrong thing. Optionally derive `unique_id` from email plus a 10 minute bucket for ad-landing sign-ups so near-simultaneous writes collapse even with different `eventId`s (trade-off: a deliberate second sign-up in the same bucket is dropped in Klaviyo but still gets a profile-level subscribe).

3. **major, R3.3, unverified.** `unique_id` dedupe on the events API: Klaviyo documents `unique_id` as "if repeated for the same profile and metric, only the first processed event is recorded". There is no Klaviyo SDK in `node_modules` and nothing in the repo (`docs/`, tests, evidence) proves it; every existing evidence file only shows the code sending a timestamp-based id. Mark R3.3 as UNVERIFIED in the spec. Add a human check before deploy: send the same `unique_id` twice to a test profile (`team+s1test-*@ekuzo.gg`) and confirm one event in the profile timeline. Note the dedupe is per profile and metric, so it does nothing across different emails (fine).

4. **major, R3.2, key scope.** `GET /api/profiles` needs `profiles:read`. The repo shows this key is custom-scoped, not full access (`docs/ekuzo101-pilot/04-evidence-ledger.md` R13: "metrics:read scope unavailable on API key"). The only proof `lookupAdName` works is unit tests with a mocked `fetch` (`outbox.test.ts` ~417 to 446) and fixture-looking Discord samples (`docs/season1-commit/analytics/evidence/discord-format.md`, `parent@example.com`). `lookupAdName` swallows every non-200 silently and logs nothing, so a 403 would be invisible today and W3 would silently do nothing in production. Fix: (a) pre-deploy gate: curl the profile filter with the production key (via Netlify env, from Jamie or a deploy preview with the prod key) for a known profile, expect 200; (b) log `status` only (no email) on non-200 from the new lookup, so Netlify logs show scope or 429 problems. State in R3.2 that "fails open" must still be observable.

5. **major, R3.2, timeouts.** The 9.2 s worst case leaves 0.8 s for cold start, body parse and response against a 10 s ceiling. The caps are correlated (a degraded Klaviyo slows the lookup, event and subscribe together), so the worst case is the likely failure mode, not a corner. A cold Next function on Netlify can alone take 0.5 to 1 s. Result: a 504 after the event was written (leads straight into item 1). Fix: run the subscribe and the CAPI send concurrently with `Promise.all` (saves up to 2 s), or cut the lookup to 1.0 s and the event to 3.0 s; require the route to compute remaining budget from a start timestamp and skip the lookup when the request already ran long. Also confirm the site function timeout in Netlify UI (the repo has no `[functions] timeout` in `netlify.toml`, so 10 s default applies).

6. **major, R3.1, lost subscription.** The first sign-up treats a failed list subscribe as non-fatal (route lines 344 to 351) and the property is already written. Any retry inside 24 h now returns `repeat:true` without ever re-trying the subscribe, so that parent is on no list and gets no email, with the client showing success. Fix: on the repeat path still call the (idempotent) subscribe, or only treat as repeat when a `season1_subscribed_at` marker exists. State the choice in R3.1; update "writes no list subscription".

7. **minor, R3.1, rate limit.** The new read runs on every unauthenticated main sign-up that passes the honeypot. Klaviyo `GET /profiles` has a lower steady limit (about 700/min) than events, and it shares the key with `lookupAdName`. A bot burst gets 429s: dedupe disappears (fail open) and the Discord commit Source lookups return null. Fix: place the lookup after the honeypot, step and email validation (spec should say so), keep fail open, and note the shared budget.

8. **minor, R3.1, enumeration.** `repeat:true` reveals that an arbitrary email signed up in the last 24 h. Low sensitivity, but it is an oracle. Options: return identical body for both cases and carry `repeat` only when the request includes the matching `eventId` (item 1 gives this for free), or accept and note it.

9. **minor, R3.1, window keyed on `season1_joined_at`.** The route is the only writer in the repo (grep), and repeats write nothing, so the window is not sliding. Risks left: Klaviyo imports or flows that set the property, and a hand-edited property in the UI. Also compare with the server clock only (Netlify lambda), never a Klaviyo timestamp; R3.2's "future-dated fails open" covers skew. Add one test where `joined_at` is exactly 24 h minus and plus 1 s.

10. **minor, R3.5/R3.6.** Client rules are fine, but "tied to the email" needs normalization: compare trimmed lowercase, or `A@x.com` then `a@x.com` makes a new id for the same person and defeats item 1's retry matching.

## W1 (join as a clone of B)

11. **major, R1.1, route config.** Next.js reads `dynamic` and other segment config statically from each route file; a value re-exported from another module is rejected at build ("can't recognize the exported `dynamic` field... needs to be a static string"). So `export * from "./b/route"` on `app/season1/join/route.ts` will not carry `force-dynamic` and may fail the build. A literal `export const dynamic = "force-dynamic";` must sit in both files. Fix: put the handler in a shared module (for example `lib/season1/joinRoute.ts` exporting `joinGet(request)` and the template path), and have both routes be `export const dynamic = "force-dynamic"; export const GET = joinGet;`. R1.1's "one shared source" is met and `b/route.ts` stays a two-line change (but note the non-regression list says `app/season1/join/b/*` is zero diff; reconcile: either allow that file to change or have `/join` import `GET` from `b/route.ts` and declare its own `dynamic`).

12. **major, R1.5, tests.** I ran `joinPage.test.ts` pointed at `join-b.html` in a scratch copy: 2 of 7 fail (`open in test mode: CTAs, test bar, jersey line, config prices` and `ladder and ages come from config`) because the assertions encode A's copy. Moving the tests is not mechanical; they must be rewritten against B's structure. Other readers of `join.html` to change: `devView.test.ts:17`, `warmRoute.test.ts:81`, `tags.test.ts:331`, and the route at `app/season1/join/route.ts:18`. `join-b.html` does include the `s1-devview.js` script (grep 1), so that test will pass once repointed. Add "tests that read join.html" to R1.5 explicitly with the list.

13. **minor, R1.5, file tracing.** No `outputFileTracingIncludes` exists; tracing works today for `/join/b` via the literal `path.join(process.cwd(), ...)` pattern, and a shared module keeps that literal. Keep the path as a literal in one place (not built from a variable) and verify on the deploy preview that `curl -s /season1/join | head` returns HTML, not a 500. A fs read failure would be a 500 for all ad traffic to `/join`. Add that curl (both paths, status 200 and equal body hash) to the evidence list.

14. **minor, R1.3.** Add a test of the closed and `mode off` render for `/join` through the shared handler, since A's template had its own `<!--IF:...-->` blocks and B's may lack `closed` markup (diff of stripped text between the two is 154 lines; the R1.6 ledger should be taken with the same `now` and `mode`).

## W4 (hero CLS)

15. **major, R4.1/R4.2, control choice.** `d21` is the same family as `d19`: `tpl:"d11"`, `cls:"s1j s1j-front"`, same file-served `team-walk-hd` and `southie-*` images, same `T.d11` bridge and font (`T[k]=T.d11` for d19 to d21). It is not an unaffected control. Use `?ad=d16` (data-URI image, no jersey) and `?ad=d1` (interactive hero) as controls, and measure `d19`, `d20`, `d21` all.

16. **major, R4.1, root cause not established.** Static reading finds nothing d18 or d19 specific in the hero box: `.art` is `aspect-ratio:4/5` with `container-type:inline-size`, `.ph` and `.jb` are `position:absolute`, so image load does not resize the box. Likely common-mode causes, to be separated by measurement, not assumed:
   a. `#hero` is empty in the HTML and filled by `innerHTML` from a 1.3 MB inline script at the end of body (`landing.html` ~1221, 1.3 MB); if the parser paints before the script runs, the form and every section below jump down by about 469 px at 375 px wide. This hits all ads, not only d18 and d19.
   b. `--disp` fonts (`Inter Tight` 800 for d18, `Rubik` 900 for d19) are chosen at runtime, so the browser only fetches them after the JS-injected text exists; `display=swap` then reflows `#bridge` and `.join h2` (uppercase 34 px display text) below the hero. d19 and d18 rely on faces not used by the static markup.
   c. d19 to d21 images are network files (`/images/season1/jersey/*.webp`, 70 to 145 KB, no `width`/`height`, no preload) versus data URIs for d1 to d17; that changes paint timing but not layout, so it matters only if (a) holds.
   Fix to R4.1: require the evidence to name the shifting nodes (use `entry.sources[].node` from layout-shift entries) for d18, d19 and the control, before choosing a fix.

17. **major, R4.3/R4.2, fix hazards.** The obvious fix (reserve space with `#hero{aspect-ratio:4/5}` or `min-height`) must be mobile only: at 960 px and up `.lp > #hero` is a sticky flex column with width `min(100%, (100vh-140px)*.8)` (line 775), and `.lp.has-ihero > #hero{display:none}` on phones for interactive heroes (line 829), where a reservation would add blank space and break R4.3 parity for d1 to d10. Heroes are decided in JS (`AD_HERO`, `?hero=`, the d10 random split in `localStorage`), so CSS alone cannot know which case applies. Suggest: a tiny inline script at the top of body that sets a class on `.lp` before first paint only for ads that use page A (d11 to d21, via the same `T` keys), and reserve space only under that class at `max-width:959px`; or defer showing `#join-top` until the hero is injected. Either way, add `<link rel="preload" as="image">` is not needed (images are absolute).

18. **minor, R4.2, how to measure reliably.** No `lighthouse`, `playwright` or `puppeteer` in `node_modules/.bin`. Method: Chrome headless (puppeteer-core or Lighthouse CLI) at 375x667, DPR 2, mobile UA, CPU 4x slowdown, Slow 4G network; inject a `PerformanceObserver({type:"layout-shift",buffered:true})` via `evaluateOnNewDocument`, ignore `hadRecentInput`, run until `load` plus 3 s, take the median of at least 7 runs and report the max session window (the metric Chrome and Lighthouse use) as well as the plain sum (what R4.2 says; pick one in the spec). Pitfalls: Google Fonts blocked in a sandbox means no swap, so CLS reads falsely low (verify the font request succeeded in the trace); cache must be cold for the first run and the test must disable cache; a 1.3 MB inline script parses faster on a laptop, hence the CPU throttle; do not use `?preview=done`. Record entries, node selectors and values in the ledger, before and after.
