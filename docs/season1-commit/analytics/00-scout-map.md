## 6. Speed slice

- Welcome route awaits the drain at `welcome/route.ts` L108 (after `fulfilFromReturn`, status paid) and L128 (a pending order found paid by `fulfil(..., "welcome")`), each `drainOutbox({limit:20, budgetMs:3000})`, before rendering. The drain has no `orderId` filter there, so it works the oldest 20 pending rows in the whole outbox; it never throws (`outbox.ts`), and on budget expiry returns with rows `in_flight` (recovered after 5 min by stuck recovery).
- Webhook: `stripe-webhook/route.ts` L222-262: verify signature, `insertEvent`, dedupe on `getEventProcessed`, `handle()` (calls `fulfil(piId,"webhook")` L113, L138), `markEventProcessed`, then `drainOutbox({limit:20,budgetMs:3500})` L260, then reply. Same outbox.
- Idempotency: `fulfil()` (`fulfil.ts` L337) returns from one read if `fulfilledAt` is set; `fulfilWithPi` claims the paid transition; `runPaidSteps` (L199-257) is documented idempotent; `enqueueOutbox` is `insert ... on conflict (dedupe_key) do nothing` (`db.ts` L449-462), keys `klaviyo_committed:<ref>`, `meta_purchase:<ref>`, `discord_commit:<ref>` (L250). Rows are created by `fulfil`, called from either the webhook or the welcome route (`fulfilFromReturn` L106, `fulfil` L124), whichever reaches a succeeded PaymentIntent first. Send claims are conditional updates (`outbox.ts` `processRow`), so concurrent drains do not double-send.
- `after()` / `waitUntil`: not used anywhere in `app/` or `lib/` (grep; the `after(` hits are node:test hooks). Installed versions cannot be read: no `node_modules` here. `package.json` pins `next 16.4.3`, `react 19.2.4`; `@netlify/plugin-nextjs` is declared only in `netlify.toml` (`[[plugins]]`) with no version, so Netlify picks it at build (check the deploy log). ## Risks and surprises

1. Handoff step 2 would collide with `attribution.origin`: that key already means "request origin URL" for test-mode share links. `ekuzo_origin` needs a different key.
2. `attribution` is insert-only on a new family. A returning parent's later utm/fbp/fbc would not be recorded unless the write path changes (a new order on an existing family also never touches it). Order-level attribution would need a place on `s1_orders` or a family update.
3. utm_*/fbclid/gclid are lost between join and signup (only `src` is forwarded), and crew to signup forwards nothing. Capture must happen where the ad click lands (join) and survive to signup via storage or the cookie.
4. The 11-02 ad URLs land on `/season1/join`, which has no Pixel. Existing live ads optimize for Lead on `/season1`; there is no Meta campaign aimed at the commit funnel yet.
5. Server Purchase has no browser pair today (all Purchase is SERVER). Pixel Purchase eventID must equal the order public id. EMQ for Purchase is 6.2 without fbp/fbc.
6. Test-mode leakage is wider than F2: landing `LIVE` includes `netlify.app` (real Pixel Lead, GA `generate_lead`, `/api/season-one` POST); the layout Pixel already fired from `dev--ekuzo.netlify.app`; adding Pixel Purchase to a test-mode welcome page would reach the live dataset (CAPI is protected by `test_event_code`, a browser Pixel is not).
7. Crew URL carries the family code in the path; Pixel PageView and Clarity record it. Welcome renders kid names, receipt and share code in the DOM; sign-up holds parent email/phone and kid names in inputs. No Clarity masking exists anywhere.
8. `thanks` page `?play=` was deliberately kept off Meta; early-access pages still carry GA only.
9. Welcome-page speed: the two drains work the global oldest-20 queue, not the order's rows, so one slow Klaviyo/Meta/Discord send for another order can also hold this parent's render (up to 3 s each, twice possible if both branches run).
10. F15: only commit.ts L299 follows a possible charge, but the client treats every 503 and 500 identically (L474). Back-forward clears client state (L524) so a retap re-enters this path.
11. Cannot run the unit suite in this sandbox without `npm ci`; counts above are from the ledgers. `@netlify/plugin-nextjs` version is unpinned and unreadable here; `after()` support must be confirmed from the deploy log or a test deploy.
12. The Google Ads tag (18509911105) is not in the repo, so a code change that removes or gates `gtag('config')` is the only repo-side lever; Ads-side linking lives in the GA4 property.
