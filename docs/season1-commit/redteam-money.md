# Season 01 commit, slice 1: money and fraud red team

Target: `02-frozen-spec.md` (draft). Read with `01-requirements.md`, the KB hub decisions (not reopened) and PM
scope sections 2 and 3. Read only; no code changed. Most severe first.

| # | Finding | Severity | Concrete fix to the spec |
|---|---|---|---|
| 1 | Webhook inserts `s1_events.stripe_event_id` and treats a duplicate as done. If `fulfil` then fails (Neon wake, timeout) the handler returns 500, Stripe retries, the retry hits the existing row and returns 200: the payment is never fulfilled. PM scope I1 said "insert event id, fulfil in one transaction"; the spec dropped it. | critical | Insert the event row and run fulfil in one transaction (Neon `Pool`), or add `processed_at` and treat a duplicate as done only when `processed_at` is set. Integration test: fail fulfil once, replay, expect one paid order. |
| 2 | `fulfil` claims with one `UPDATE` and then mints the code, updates kids, inserts events and outbox as separate statements. A crash after the claim leaves an order `paid` with no code or outbox, and every later call sees "not claimed" and no-ops forever. | critical | Run claim plus all inserts in one transaction (`sql.transaction` or `Pool`); or add `fulfilled_at`, and when the order is paid with `fulfilled_at` null, rerun the idempotent post-claim steps. |
| 3 | Every submit POSTs `/commit`, which creates a new order and a new PaymentIntent; the idempotency key `s1-commit:<order public_id>` is new each time, so it dedupes nothing. A double tap, two tabs, a fetch timeout retry, or a decline retry each make a separate PI that can each be confirmed (two charges), leave orphans, and burn the 5 per IP limit for a parent who just had a decline. | critical | Client sends an `attemptId` (UUID in sessionStorage); server keys order and PI on (`email`, `attemptId`) and returns the existing `clientSecret` when kids and amount are unchanged, else cancels the old PI and makes a new one. After a decline the client re-confirms the same `clientSecret` with no new POST. |
| 4 | Card testing is done at confirm, not at create. One `clientSecret` can be confirmed again and again with different cards, so the per-IP limit on PI creation never fires. The IP key falls back to `x-forwarded-for`, whose first hop the client sets; the honeypot stops only dumb bots. | critical | On `payment_intent.payment_failed`, count failures per PI; at 3, cancel the PI and flag. Key limits only on `x-nf-client-connection-ip` (IPv6 bucketed by /64; header missing means one shared bucket). Add a global ceiling (for example 60 PIs per hour) and a breaker that sets the API to `closed` when failures in an hour pass a threshold. Turn on Radar card-testing rules before live. |
| 5 | Deferred intent requires the Elements `amount` to equal the PI amount. The client builds `amount` from config, but the server quote uses `priorPaidKids` (a returning family's first kid is $80). The amounts differ, so confirm throws, and the wallet sheet already showed $100. Each retry adds another orphan PI. | major | Client sends `expectedCents`. If the server quote differs, return 409 `{error:"price_changed", amountCents}` before creating any PI; the client calls `elements.update({amount})` and asks for a second tap. The server still never uses the client's number. Add an E2E test for a returning-family $80 order. |
| 6 | Customer "search by email, reuse newest": Stripe search is eventually consistent (about 1 minute), so concurrent commits make duplicate Customers. Reuse also attaches Season 01 to legacy Teams or camps Customers: in December, credits posted as negative customer balance (architect plan) would be eaten by legacy Teams invoices, and the default payment method gets mixed up. | major | Drop Stripe search. Create one Season 01 Customer per `s1_families` row with idempotency key `s1-cust:<family id>`, store it, and reuse only that one. Metadata `product=season1`. Lock-in charges use each order's `payment_method_id`, never the customer default. |
| 7 | Email squatting: anyone who types a victim's email upserts that family. They can overwrite the guardian's name and phone, add kids to the victim's family, get the $80 sibling price, and trip the victim's 20 per day email limit (a lockout). | major | Guardian rows are insert-only from `/commit`: on an existing email, store the submitted parent name and phone on the order as payer fields and leave the guardian unchanged. In fulfil, flag `email_reuse_new_card` when the card fingerprint differs from the family's earlier paid cards. Count the email limit only on attempts that reach confirm. |
| 8 | Orphaned PIs stay confirmable forever. A tab left open past `closeAt` or the jersey cutoff can still pay. `jersey_eligible` is fixed when the PI is created, which drops M5's "paid within 24 hours": create Nov 30, pay Dec 20, get a jersey. | major | Compute `jersey_eligible` in fulfil as `pi_created_at < jerseyCutoffAt AND paid_at - pi_created_at <= 24h`. Cancel pending PIs older than 24 hours (in `s1:outbox` or the next commit on the same email). Flag `late_confirm` when `paid_at >= closeAt`. |
| 9 | `automatic_payment_methods: {enabled: true}` with `setup_future_usage` shows whatever reusable methods the Dashboard enables (ACH bank debit, Cash App Pay, Amazon Pay). ACH is asynchronous: `processing` for days, then it can fail after the welcome page. The architect asked for "only reusable methods (cards, wallets, Link)". | major | Server: `payment_method_types: ["card","link"]` (Apple Pay and Google Pay ride on card). Client: `paymentMethodTypes: ["card","link"]` in `elements()`, so both sides match as the deferred flow requires. Fulfil treats `processing` as pending. |
| 10 | The mode is a kill switch. If it gates the webhook or the welcome fulfil, flipping to `off` while PIs are in flight takes money that is never recorded, and the welcome page shows "closed" to families who have already paid. | major | State it outright: mode gates PI creation and the signup page only. The webhook and welcome fulfil always run and show paid orders. They check `event.livemode` and `pi.livemode` against the key prefix and skip a mismatch with 200. |
| 11 | The cookie `s1_order` holds the order public id. That same id is the receipt's "order reference" (C13), Meta's `event_id` (I5) and GA's `transaction_id` (A1). Anyone with the id (a screenshot, GA access, Meta) can set the cookie and see kid first names, the code and the amount. | major | Add `s1_orders.view_token` (32 random bytes, stored hashed). The cookie carries the token, and the welcome page looks orders up by it. The public id is only a reference and never grants access. |
| 12 | The welcome page needs the cookie. 3DS or bank-app returns and Instagram or Facebook in-app browsers often come back in another browser or a fresh webview with no cookie: generic page, no share link, and fulfil depends on the webhook alone. | major | When the query has `payment_intent` plus `payment_intent_client_secret` and the secret equals the retrieved PI's `client_secret`, treat that as proof of ownership: run fulfil, set the `view_token` cookie, then 303. Use the cookie path only when the query is absent. |
| 13 | Refunds are recorded as event rows only until slice 5. A family refunded in the Dashboard stays `paid`, so it keeps sibling pricing (`priorPaidKids`) and a working code, and a refund issued before fulfil still mints a code and queues Committed. | major | Slice 1 sets `status='refunded'` when `amount_refunded = amount` on `charge.refunded`. `priorPaidKids` counts only `status='paid'`. Fulfil retrieves with `expand: ["latest_charge"]` and, when anything is refunded, claims as `refunded` with no outbox. |
| 14 | Legacy handler: `getProductFromMeta("season1")` falls back to camps, so a season1 PI that reaches it fires a camps Beehiiv enrolment, Klaviyo Placed Order, Sheets rows and a second Meta CAPI Purchase. The guard is only "lines in route.ts" with no stated position. | major | Make the guard the first statement after signature verification, before the mode check and `charges.list`. Skip when `meta.product === "season1"`, when `parent_email` is missing, or when `meta.product` is set but is not a known id (catches typos and future products). Fixture test for each case. |
| 15 | Duplicate paid kids: the P6 guard is in slice 2, and P6 only checks earlier paid orders, so two pending orders for the same kid (two tabs, two parents) can both be paid. | major | Fulfil flags `duplicate_kid` (same folded first name on another paid, unrefunded order for this family within 30 days) for a hand refund. The P6 check at commit also covers pending orders that have a live PI on the same email. |
| 16 | Fulfil checks only `metadata.product` and `status`. It does not check that the PI's amount and currency equal the order's, that `metadata.order_id` matches the row found by `payment_intent_id`, or livemode. | minor | Require `pi.amount === order.amount_cents`, `currency === "usd"`, `metadata.order_id === order.public_id` and `pi.livemode === order.livemode`. On a mismatch, record the event, flag it and claim nothing. |
| 17 | Live gating uses "request host". If the host comes from `x-forwarded-host` or `nextUrl`, the header can be spoofed, and live never checks the database (live money could land in the test DB that previews share) or that the publishable key prefix matches. | minor | Live requires `sk_live_` and `pk_live_`, a `DATABASE_URL` without the test endpoint, `S1_STRIPE_WEBHOOK_SECRET` set, and Netlify `CONTEXT=production` read at build time. Host is checked against the raw `host` header only, as an extra check. Any miss means `off`. |
| 18 | The S1 webhook records `charge.refunded` and dispute events for every product, which puts camps and Teams parent PII in `s1_events.data`. Charges don't carry the PI's metadata, so a naive product filter misses them. | minor | For charge and refund events, retrieve the PI (`charge.payment_intent`) and record only when `metadata.product === "season1"`. Otherwise return 200 with nothing written. |
| 19 | The Express Checkout path is not spelled out. The wallet `confirm` handler must call `elements.submit()`, POST, then `confirmPayment`, and call `event.paymentFailed()` on a server error. Apple Pay `recurringPaymentRequest` needs `managementURL` and `regularBilling` amounts per kid count (siblings at $128), or there is no MPAN and lock-in charges risk failing. | minor | Add an ECE `confirm` sequence to the spec. Build `recurringPaymentRequest` from the server quote. In fulfil, record `payment_method.type`, `card.wallet.type` and the fingerprint. The real-device check confirms that an Apple Pay PM saved on the Customer is usable off-session. |
| 20 | The consent record (M4) takes `consent_ip` from `x-forwarded-for` as a fallback, so the client can forge the IP it was given from. That weakens the record behind later saved-card charges in a dispute. | minor | `consent_ip` comes only from `x-nf-client-connection-ip`. Also store the raw `x-forwarded-for` in its own column, labelled as client-supplied. |
