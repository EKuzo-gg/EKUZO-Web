Locked decisions not reopened: the inviting kid's first name on the invite page; no kid names in URLs or GA;
payer separate from guardian. Kids are 9 to 18. Read only; 2026-10-26 late evening.

| # | Finding | Severity | Spec fix (one or two lines) |
|---|---|---|---|
| 1 | "Joining {Kid}'s team" promises co-placement with a named child to anyone holding the link. A kid who posts the link publicly (TikTok, a League Discord), or an adult posing as a 17-year-old, can pay $100 and ask to be on that child's team. Nothing in the spec says the referral is not a placement instruction. | critical | Add the rule "a referral never drives placement; a same-team request is confirmed by Karlin with both parents, never for `burst` codes". Delta for Aaron: banner and invite CTA read "Join with {Kid}'s family" or similar, not a team promise. |
| 2 | Inviting parents are told only in the privacy policy that the link shows their kid's name to anyone who opens it, and there is no way to retire a link once a kid posts it publicly. `burst` only alerts Discord. | major | Welcome share block adds "Anyone with this link sees {Kid}'s first name. Share it with families you know." Add an ops `rotate(family)` snippet (void the code, mint a new one) and `s1_codes.show_name` (Karlin sets it false on request or on `burst`); false renders the nameless page. Neither one edits the display name. |
| 3 | Vanity codes (`^[a-z]{3,20}$`, Karlin by hand) can be guessed from a dictionary and can reveal identity: `smith` or `thejohnsons` resolves to a kid's first name, which gives a minor's full name and enrollment. | major | Vanity rows are only for `partner` or creator use and render the partner's display name or the nameless page, never a family kid's name. The ops note forbids surnames and kid names in vanity strings. |
| 4 | The signup page is a name oracle that the R5 limit does not cover: set `s1_ref` to any code by hand (the cookie is not HttpOnly or signed), load signup, and the server injects the kid's name. R5 is per IP only, with no IPv6 /64 bucketing for lookups and no global cap, so rotating IPs can walk the 9M space. | major | Sign `s1_ref` (code plus HMAC, set only by `/crew`); signup and commit ignore unsigned values. Put the R5 limit inside `resolveCode` for every caller, with /64 buckets and a global cap (for example 300 named renders an hour, then nameless plus a Discord alert). |
| 5 | Codes and names leak to GA: (a) `/season1/crew?from=Name` stays live until slice 4 and its GA `config` sends `page_location` with the kid's name; (b) the clone may keep the `?from=` script and its "Charlie" fallback; (c) the signup page's GA `page_referrer` is the full `/crew/<code>`; (d) an extra `gtag('config')` sends a page_view before the override. | major | Move the `/season1/crew*` 301 (query dropped) into slice 2. Delete the `from` script and the "Charlie" fallback from the clone. Send `Referrer-Policy: origin` on `/crew/*`. Keep a static `<title>`. Use exactly one `config` call carrying the `page_location` override. Test: captured `collect` hits contain no code or name. |
| 6 | Link unfurlers fetch the server-rendered name: `facebookexternalhit` (Instagram, Facebook, Messenger), WhatsApp, Discordbot and iMessage. That sends kid names to Meta (a must-not) and into preview cards. They also use up the per-IP lookup budget. | major | Use a static title and static `og:*` tags with no name. Serve the nameless variant to known crawler user agents and leave those requests out of the R5 counts. |
| 7 | The banner and "Feb 15: free, from {Kid}" appear before the email is known. Commit then ignores the code silently (own family, already-paid family, code voided after render). The parent paid expecting a credit that was never recorded, which breeds trust problems, refunds and disputes. The totals line also leaves "is today free?" open. | major | The commit response returns `invite: "applied"\|"ignored"` (plus a reason) before `confirmPayment`. If ignored, the client drops the banner and credit line and shows one line before charging. Totals read "Today $100. Feb 15 $0 with {Kid}'s credit, applied at lock-in." Welcome and receipt state whether a friend credit was recorded. |
| 8 | Over the rate limit, or behind shared IPs (carrier NAT, which in-app traffic often uses, or school Wi-Fi), the page renders nameless and does not set `s1_ref` ("only when the code resolves"). The referral is lost with no trace, for both families. | major | When rate-limited or skipped as a crawler, still set the signed cookie for any Damm-valid code (signup and commit resolve it anyway); only the name is withheld. |
| 9 | Remove might not stick. A client-side expire must match the cookie's Path and Domain exactly. If it doesn't, commit still reads `s1_ref` and records a referral the parent declined, and the inviter gets "Friend Joined". The Remove label also hides its cost and the fact that the other family is told. | major | Remove calls a small endpoint that clears the cookie server side (which lets the cookie become HttpOnly), and the commit body carries `inviteRemoved: true`, which the server honors. Add a test: no referral after Remove. Copy: "Remove (no $160 credit for either family)" and "{Kid}'s family gets a note that a friend joined, with no names." |
| 10 | Instagram and Facebook in-app browsers keep their own cookie jars. A parent who opens the link in the app and pays later from email in Safari or Gmail sees no banner and gets no credit. R6 (Karlin attaches a code) is only a Should, so there is no recovery path. | major | Show the display code on the invite page ("Friend code 4827 1937"). Welcome adds "Came from a friend's link and no credit shows? Text Karlin the code." Promote R6 to Must in slice 2. |
| 11 | Anyone who knows only an email, without paying, can use commit to learn that the address has a paid order (`amountCents` 8000 or `price_changed`) and to confirm a kid's first name (409 `duplicate_kid`), i.e. that a named child is enrolled. That matters in custody or estrangement cases. Commit also attaches the submitted kid rows to the real family before any payment. | major | Count every commit call, 409s included, against the IP and email limits. After 3 `duplicate_kid` hits on one email in a day, return a generic "Text Karlin" and flag Discord. Kids from unpaid orders never appear in ops views or name resolution. Record the residual sibling-price signal as accepted. |
| 12 | There is no deletion runbook (N5 says "by hand"). Kid names sit in `s1_kids`, vanity rows, Klaviyo (`kid_name`, `sibling_names`, and the joiner's `invited_by_kid`, which puts another family's kid on someone else's profile), Discord alerts and the Sheets mirror. | major | Drop `invited_by_kid` from the joiner's Klaviyo payload (use `invited: true`). Add a deletion checklist to the ops notes: void the code and its vanity rows, null kid names while keeping counts, scrub Klaviyo properties, delete Discord posts found by code, remove the Sheet rows, log the request. |
| 13 | The name shown is "the first kid of the earliest paid order" even after that kid has been refunded, withdrawn or deleted, so a child no longer in the program stays named on a public page. | minor | Resolve to the first kid whose status is `committed`; if there is none, render nameless. |
