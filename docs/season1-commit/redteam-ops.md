# Season 01 commit, slices 1 and 2: operations and failure red team (lens 3)

Targets: `02b-spec-slice2.md` (draft), `02-frozen-spec.md` including "Red team resolutions",
`03-decision-log.md`, and the code present at 22:30 CT (`lib/season1/db.ts`, `mode.ts`, `ratelimit.ts`,
`db/migrations/0001`, `0002`, `scripts/s1-migrate.mjs`, the welcome route). Read only. Most severe first.

| # | Finding | Severity | Concrete fix (spec change or launch checklist item) |
|---|---|---|---|
| 1 | Rollback breaks fulfil. `getSql()` allows a non-test DB only when `S1_COMMIT_MODE === "live"`. Setting the mode to `off` in production makes every DB call throw "Refusing", so the webhook returns 500, welcome shows the generic page, and in-flight 3DS payments and refunds go unrecorded. A Netlify env change also needs a redeploy, so "mode off" is not instant. | critical | Spec: the DB guard keys on deploy context, not commit mode (prod DB allowed only when `CONTEXT === "production"` and host is ekuzo.gg; test marker otherwise). Add a runtime kill switch read per request (a `s1_settings` row, cached 30 s) for the commit API. A 409 `closed` on a loaded page shows "Signups are paused. Text Karlin." |
| 2 | `livemode` defaults to `false` on `s1_events`, `s1_outbox`, `s1_order_items`, `s1_rate_limits`, and `enqueueOutbox(..., livemode = false)` / `insertEvent(livemode ?? false)` default it in code. A live fulfil that forgets the argument tags real purchases as test. The slice 3 sender then sends Meta with `test_event_code` and treats the row as test. | critical | Migration 0003: drop the defaults (NOT NULL, no default). Code: make `livemode` a required parameter. The sender reads livemode from the order row, not the outbox row. Unit test: live fulfil writes `livemode=true` everywhere. |
| 3 | A succeeded Season 01 PI that matches no order row (for example, `setOrderPaymentIntent` failed after the PI was created, or a 3DS return after a cancel and retry) makes the claim find nothing. Fulfil no-ops, the webhook sets `processed_at`, and a paid family is lost silently. | high | Spec: fulfil looks up the order by `pi.metadata.order_id` when `payment_intent_id` misses, then backfills it. If there is still no order, record `orphan_paid_pi`, outbox an alert, and return 500 without setting `processed_at`. Integration test: null the stored PI id, then replay. |
| 4 | Partial refunds can't name a kid. A Dashboard refund of $80 from a $180 two-kid order sets the order to `partially_refunded`, but no kid becomes `refunded`. `priorPaidKids` still counts that kid, the P6 duplicate guard blocks re-adding them, and the referral keeps `friend_kids=2`, so the inviter is credited for a kid who left. Split refunds that sum to the full amount must also read as full. | high | Spec: refunds go through `scripts/s1-refund.mjs --order <ref> --kid <name>`, which creates the Stripe refund with `metadata.s1_kid_id`. The handler marks that kid refunded and decrements `friend_kids`. A refund without metadata is flagged `refund_unattributed` and alerts. "Full" means `charge.amount_refunded === charge.amount`, not the event's refund amount. |
| 5 | Welcome-page fulfil hides webhook misconfiguration. A missing or wrong `S1_STRIPE_WEBHOOK_SECRET` on a deploy context, or a live endpoint missing `charge.refunded` or `payment_intent.payment_failed`, returns 400 or nothing. Card payments still look fine because welcome fulfils them, but refunds, failure counts and closed-tab payments go unrecorded until Stripe's failing-endpoint email arrives days later. | high | Launch checklist: create the live endpoint in the Stripe Dashboard for `/api/season1/stripe-webhook` with the 6 events from the spec. Scope `S1_STRIPE_WEBHOOK_SECRET` (live value) to Production only. Confirm the legacy endpoint is unchanged. Canary: Jamie pays $100 live and refunds it, then checks that `s1_events` has both events with `source=webhook`. Spec: alert when an order is fulfilled by welcome and no webhook event arrives within 15 min. |
| 6 | Nobody sees anything overnight. Until the slice 3 sender exists, no alert fires for webhook 500s, `pi_mismatch`, card-testing breaker trips or orphan PIs. Netlify function logs are short-lived and unsearchable by family. | high | Launch checklist: turn on Stripe "successful payment" and "refund" email notifications for Jamie and Karlin. Spec: one PII-free log line per step (`s1 step=fulfil order=<public_id> ok=false err=<code>`, never email, name or IP). Add an hourly Netlify scheduled function that compares Season 01 PIs that succeeded in Stripe in the last 24 h with paid orders and outboxes `ops_alert` rows (Discord in slice 3). |
| 7 | The global ceiling of 60 PIs per hour (RT4) can block real parents during the 250-lead blast. Each page load mints a new `attemptId`, and `price_changed` and decline paths add PIs. A 20% click-through in one hour reaches the cap, and paying parents get 429. | high | Spec: raise the ceiling to 300 per hour and add a breaker keyed on `payment_failed` per hour, not on creation count. Alert at 50% of either limit. Launch checklist: send the blast in 2 or 3 batches about 30 min apart. |
| 8 | Welcome when Neon is asleep or down. `loadOrder` turns a DB error into `null`, so a parent who has just paid gets the generic page with no share link and no auto-refresh. A thrown `fulfilFromReturn` also skips the fresh view-token cookie. | high | Spec: a DB error renders the pending state (meta refresh 4 s, at most 5 tries, then "Your payment went through. Your link is on its way. Text Karlin."). Only a confirmed missing order shows the generic page. |
| 9 | A family that refunds and then rejoins gets stuck. Their family code is `void`. `mintFamilyCode` returns the existing void code (the partial unique index blocks a new one), but `getOrderByPublicId` selects only active codes. Welcome requires `order.code`, so the paid family loops forever on "We're confirming your payment". | medium | Spec: on a new paid order, fulfil sets the family's void code back to `active` (one statement, in the idempotent steps). The welcome paid state does not depend on a code being present. Integration test: pay, fully refund, pay again, welcome shows the code. |
| 10 | Launch order and env scoping. The production DB is empty and `0003` comes from Relay B. `getSql` lets any context reach the prod DB when the mode is `live`. If `DATABASE_URL` and `S1_COMMIT_MODE=live` are set for "all contexts", previews and branch deploys read and write production. | high | Launch checklist, in order: (1) note the Neon PITR point; (2) run `s1-migrate.mjs --live` locally against prod and check `s1_migrations` has 0001 through 0003; (3) scope prod `DATABASE_URL`, live keys, the live webhook secret and `S1_COMMIT_MODE` to Production only (previews keep the test values); (4) deploy with the mode unset, so it resolves to off; (5) create the webhook endpoint; (6) set `live` and redeploy; (7) run the canary from row 5. |
| 11 | Outbox backlog. Rows pile up from tonight until slice 3. A naive sender then drains them all at once: "Committed" emails go out days late, Meta drops events older than 7 days, and test rows from the shared test branch reach the one real Klaviyo account and its flows. | medium | Slice 3 spec: per-kind max age (`meta_purchase` 6 days; `klaviyo_*` 48 h, after which the row is marked `stale` and not sent; Discord sends a digest rather than a replay). Rows with `livemode=false` go only to `+test`/`@ekuzo.gg` addresses or a test metric name. Before pointing the sender at the test DB, mark the existing test rows `stale`. |
| 12 | Neon cold start and slow queries. The compute auto-suspends, and commit runs about 10 sequential HTTP round trips plus Stripe calls. `neon()` has no fetch timeout, so a hung query holds the function until Netlify kills it. "Webhook under 2 s" won't hold on a cold start. A Neon region far from Netlify's function region adds about 60 ms per query. | medium | Launch checklist: on the Neon prod branch, turn off scale-to-zero (or keep a 1-minute warm ping) for the launch window, if the plan allows. Check that the Neon region matches the Netlify functions region. Spec: `neon(url, {fetchOptions: {signal: AbortSignal.timeout(8000)}})` and a role `statement_timeout = '5s'`. A webhook timeout is safe because of `processed_at` and `fulfilled_at`. Check the site's sync function time limit. |
| 13 | Hand-run SQL against production. Karlin creates vanity codes and voids codes in the Neon console. A vanity row needs `family_id` (NOT NULL), `livemode` and an active target, and the spec gives no snippet for it. An UPDATE without a WHERE, or a vanity pointing at a void or test code, fails silently. | medium | Spec: `docs/season1-commit/ops-runbook.md` with reviewed snippets: find a family by email, order ref (shown on welcome and in Stripe `metadata.order_id`) or kid name; vanity `insert ... select family_id, livemode from s1_codes where code=$target and status='active'`; void; refund (row 4). Karlin gets a Neon role with SELECT on `s1_*` plus INSERT and UPDATE on `s1_codes` only. `resolveCode` checks that the vanity's target is active. |
| 14 | One shared Neon test branch serves previews, Playwright and integration tests. The global PI ceiling, per-IP rate-limit rows, the `burst` flag count and the email-day limit all leak between runs, so tests turn flaky and a test run can 429 Jamie's own preview check. | low | Spec: tests use a run-scoped email (`s1+<runId>@ekuzo.gg`) and fresh codes. In test mode, rate-limit keys are prefixed with `runId` when a header is present, and the global ceiling counts per livemode. Optional: one Neon child branch per CI run. |
| 15 | A 10-minute Stripe or Neon outage. With Neon down, commit returns a bare 500 and the page needs readable copy. With Stripe down after the DB inserts, pending orders with no PI and kids stuck in `pending` pile up and distort counts and `burst`. Webhooks retry for days (safe). A `refund.failed` after `charge.refunded` leaves the order saying refunded. | low | Spec: a 500 shows "Something hiccuped. Your card was not charged. Try again in a minute or text Karlin."
