# Auditor, phase 1: Season 01 popup attribution fix

Reviewed: `01-requirements.md` against `lib/attribution.ts`, `components/ui/SeasonOnePopup.tsx`, `components/ui/SeasonOneTrigger.tsx`, `app/api/season-one/route.ts`, `app/season1/route.ts`, `docs/season-one-tracking.md`, `app/season1/landing.html` (script at lines 842-1085), every consumer of `getAttribution` / `captureAttribution` / `"ekuzo_attribution"`, `components/analytics/CaptureAttribution.tsx`, `middleware.ts`, and the existing `lib/__tests__/season-one-attribution.test.ts`.

Consumer audit (for N4): `CaptureAttribution` (mounted in `app/layout.tsx`, runs on every Next page, never on `/season1`), `hooks/useRegisterForm.ts` (`captureAttribution` on mount), `getAttribution` in the four register pages (camps, 100, 101, teams) and in `SeasonOnePopup`. Nothing server-side and no static HTML reads `ekuzo_attribution`. The only exit from the landing page is the footer link `https://ekuzo.gg` (line 821, absolute URL). In Season 01 mode the middleware redirects every `/register` page to its program page with `?join=season-one`, keeping the query string.

Findings, most severe first.

1. **BLOCKER. A stale non-Season-01 session record beats the ad (F1 first-touch clause, F4b).**
   Reproduction: visitor opens `/blog/x?utm_source=beehiiv&utm_medium=email` (CaptureAttribution writes the session record), then in the same tab opens `/season1?ad=d5&utm_source=meta...`. F1 says write only when "no session record with a non-empty ad key exists". The beehiiv record has non-empty `utm_source`, so F1 writes nothing to the session. F4b then resolves to the beehiiv record (`session`, `ad` empty) and the return-visit record that holds the real ad is never read. This reproduces the original bug, and "ad key" is ambiguous (the Definitions list includes the utm keys, but the intent is clearly "an ad was recorded"). The same hole exists between two Season 01 landings in one session (d5 then d7): session keeps d5, return-visit holds d7, popup sends d5, which contradicts F2's "most recent ad landing wins".
   Suggested wording (recommended, one rule for both stores): "F1. On load, `/season1` writes the ad keys from its own query string to the session record whenever the URL carries at least one non-empty ad key, replacing any existing session record. A Season 01 ad landing is the last-click touch and is the one deliberate exception to first-touch; first-touch is unchanged on every other page." Add: "F1b. Test: session holds `utm_source=beehiiv`, load `/season1?ad=d5&utm_source=meta...`, session record now holds the meta values and `ad: d5`." Jamie should confirm the exception, because it also changes what camps/100/101/teams registration would send after an S1 landing (more correct, but a value change; see item 12).
   Alternative if strict first-touch is wanted: keep F1 as is and change F4b to "session record has an `ad`, or has any key and the return-visit record is absent or has no `ad`". This is weaker and leaves the d5/d7 case inconsistent with F2.

2. **BLOCKER. CaptureAttribution on a later page can overwrite the landing record and drop `ad`, `utm_id`, `site` (F1, N4).**
   `captureAttribution` decides "already captured" with `hasAny` over the five utm keys only (`lib/attribution.ts` line 61), and when it does write it stores only those five keys. Two ways this loses the record: (a) F1 stores a record with only `ad` (URL `?ad=d5`, no utm): `hasAny` is false, so a later page with any `?utm_...` (a re-entry from a Beehiiv link, a `/?utm_source=x&join=season-one` ad) rewrites the record with five keys and silently drops `ad`; (b) the same applies to a record holding only `utm_id` or `site`. A record with at least one of the five utm keys is safe (`hasAny` true, no-op).
   Suggested wording: "F1c. The session record is written only when the URL carries at least one of the five utm_* keys. A landing visit with only `ad`, `utm_id` or `site` writes the return-visit record only. Test: after a landing that wrote a session record with utm_source set, load `/?utm_source=other&utm_campaign=x` and `/`; session record is byte-identical." If Jamie prefers storing ad-only touches in the session, N4 must be reworded to allow `hasAny` to include `ad`, `utm_id` and `site`, with a test that `getAttribution()` output is unchanged.

3. **SHOULD-FIX. `attribution_from` can say "none" while `ad` is recorded (F4, F6).**
   F4 (and the existing unit tests) count an ad-only record as a touch, but F6 downgrades to `none` unless one of the seven utm/utm_id/site values is non-empty. Result: `ad: d5`, all utm empty, `attribution_from: none`. Same for the ad-landing source when the URL has `ad` but no utm.
   Suggested wording: "F6. Popup: the client's `attributionFrom` if it is `url`, `session` or `return-visit` AND at least one of the seven values or the normalized `ad` is non-empty, else `none`. Ad-landing: `url` when any of the seven values is non-empty, else `none` (the landing always sends an `ad`, so it is not a signal there; state this in the docs)."

4. **SHOULD-FIX. Record shape and resolution edge cases are not specified (F1, F2, F4).**
   Add to Definitions: "Both records are JSON objects with exactly the eight keys utm_source, utm_medium, utm_campaign, utm_content, utm_term, utm_id, site, ad, always present, empty string when absent; the return-visit record adds `at` (number); the session record has no `at`." Add to F4: "(c) applies only when the record has at least one non-empty ad key and `at` is a finite number with 0 <= now - at <= 7 days (inclusive, matching the existing unit test); a future `at`, non-number `at`, malformed JSON, non-object JSON, or a storage exception falls through to the next source." F1 `ad` validity: "same rule as the route's `normalizeAd` and the page's own parsing: case-insensitive, optional leading zero, d1..d12, stored normalized as d1..d12". Test table for `ad`: d5, D5, d05, d12, d13, d0, d, `d5x`, ` d5`, empty.

5. **SHOULD-FIX. F5 does not say where `attributionFrom` lives.**
   "carries `attribution` with all seven keys and a new `attributionFrom` string" can be read as nested inside `attribution`. Suggested wording: "`attributionFrom` is a top-level sibling of `attribution`. `attribution` has exactly the seven keys and nothing else. `getAttribution()` is not used by the popup for this; a new reader is added and `getAttribution` stays as is (N4)."

6. **SHOULD-FIX. F8 overstates what a return visit can recover (known limits to write down).**
   (a) `localStorage` is per browser storage jar. Meta ads open in the Instagram/Facebook in-app browser; a parent who later opens ekuzo.gg in Safari or Chrome has no record and gets `none` (undercount, not false credit). (b) Safari's tracking prevention may cap script-written storage to as little as 24 hours when the page was reached through a decorated link from a social domain (fbclid). The 7 days cannot be promised on iOS. (c) `sessionStorage` is not shared across tabs, so a second tab resolves via return-visit, not session.
   Suggested wording: add under F8: "Known limit: return-visit works only in the same browser profile and storage jar that loaded `/season1`; it is not expected to survive an in-app-browser to external-browser hop or Safari's storage caps. Document in `docs/season-one-tracking.md`. Out of scope: server-side cookie." Tests for F8 use one browser context only.

7. **SHOULD-FIX. F7 and F8 as written are hard to run on any non-production host.**
   The landing's only exit link is the absolute `https://ekuzo.gg`; on localhost, a Netlify preview or `dev--ekuzo.netlify.app` it leaves the origin (storage not shared). The popup only auto-opens 2.5 s after load on non-quiet pages and not at all once `ekuzo_s1_joined` is set or `ekuzo_s1_dismissed_at` is within 7 days (`SeasonOneTrigger.tsx`).
   Suggested wording for F7/F8 verification: "Navigate to `/` by URL in the same tab and origin (not by clicking the footer link). Wait for the popup (auto-open after 2.5 s or use `?join=season-one`, which does not disturb attribution). Between cases clear `ekuzo_s1_joined`, `ekuzo_s1_dismissed_at` and `sessionStorage`, but not `ekuzo_s1_attribution` unless the case is N1 or the 7-day expiry. F8 expiry is tested by seeding `at = now - 7d - 1 s` (and `now - 7d` for the inclusive boundary), not by waiting."

14. **NOTE. False-credit analysis.**
    Paid credit that does not come from an ad: (a) F1/F2 store only what the URL carried, so nothing invents `utm_source=meta` (good; keep as an explicit rule: "no default values"). (b) The default d1 on the landing page for a missing or bad `ad` is never stored (good, F1). (c) A hand-typed or shared `/season1?ad=d5` link records `ad: d5` with no `utm_source`; downstream reports should treat "paid" as `utm_source`/`utm_medium`, not as "`ad` present". (d) The 7-day return window credits an ad to a sign-up that arrives later by organic or direct (no URL keys, new session). This is by design (last click, like Meta), and `attribution_from: return-visit` is the marker; say so in the docs so reports can separate it. (e) A URL with non-Season-01 utm on the popup page (F4a) replaces a session ad: last-touch for the URL, defensible, but state it in the resolution-order doc. (f) `attributionFrom` is client-supplied and can be forged; harmless, treat as a label (F6 whitelist is enough).

15. **NOTE. The `utm_content` fallback for `ad` (F4) is dead code.**
    `utm_content` values like `d5-a-showup` never pass `normalizeAd`, so "kept for compatibility" achieves nothing. Either drop it, or derive `ad` from a validated prefix (`^d(0?[1-9]|1[0-2])(-|$)`, case-insensitive, then normalized) with a test, which would also recover `ad` for ads that land on `/?utm_content=d5-...`. Pick one and say which.

Klaviyo-side: (a) the new `attribution_from` event property; (b) popup profiles will now carry `season1_ad` (previously always empty from the popup), which changes any Klaviyo segment that uses it.
