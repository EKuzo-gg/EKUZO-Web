# Red team, lens: abuse and fraud

Spec under attack: 01-requirements.md and 02-frozen-spec.md (commit cb61c77). Read against betaWizard.ts, betaProgressScript.ts, refcookie.ts, middleware.ts, app/api/season-one/route.ts, migration 0006. D1 to D4, D10, D11 of the go-live build are accepted and not re-raised; A3 below only records what the restart link adds to them.

## Findings

| ID | Severity | Finding and attack steps | Rests on | Proposed fix |
|---|---|---|---|---|
| A1 | major | **Planted link: the victim's kid data is typed into the attacker's row, and the attacker reads it.** (1) Attacker signs up the wizard with their own email, stops after the email screen, receives their own pick-up link. (2) Attacker sends it to a target parent (message, ad comment, a page that sets location.href to it; a cross-site top-level GET is enough for a SameSite=Lax cookie to be stored). (3) Victim lands on /start; the restore returns state `resume` with the attacker's email, session and stage. The script fills the email and walks forward with the Continue buttons, so the victim never sees the email screen or any sign that it is not their address. (4) Victim types their child's name, age and answers; each step posts progress to the attacker's row under the attacker's session. (5) Attacker opens their own (reusable, L6) link, or reads the pick-up/"We got it" mail and the Klaviyo profile, and reads the child's name, age and answers. The finished sign-up and every later email go to the attacker's address while the victim sees the normal end screen. The restored state is also written to the victim's localStorage (14 days), so the attacker's email is re-applied on every later visit from that browser. | L8 "reopens the wizard on the step they left"; spec Page script (restore walk past the email step); L6 reusable link; progress posts carry `answers` for any session | A restore must put the parent in front of the email: land on the first step after the email, but show a masked "Continuing as j***@gmail.com. Not you? Start over" line above the form (generates a new session id, clears local state, no restore). Do not persist a link-restored email in localStorage until the parent has pressed a Continue on a screen that shows the masked address. Consider issuing the link only on a row the browser did not just plant (not possible server side, so the visible confirmation is the control). Add a test: restore with email A, page shows the masked A. |
| A2 | minor | **Source cookie planting and "direct" lock-in (L9).** The row's `source` column is `src \|\| utm_source tag \|\| "first-touch:..." \|\| "direct"`, and anyone can set it with a progress post (utm_source in `attribution`). L9 copies it to `ekuzo_bsrc` for 30 days if it passes `BETA_SRC_RE`. (a) Attacker posts progress for any email with `utm_source=karlin-email` (or any 40-char tag), then plants the link (A1): the victim's browser now has `ekuzo_bsrc=karlin-email`, which `betaAttribution` ranks above the victim's real last click, utm and first-touch. Ad and creator attribution is poisoned. (b) Honest case: a row whose source is the literal "direct" passes the regex, so a family that finishes on a second device is stamped `src: direct` and loses its real utm and first-touch there. | L9; `betaAttribution` (src first); `BETA_SRC_RE` accepts "direct" and any utm_source tag | Set the cookie only when the row's `attribution->>'src'` is non-null (an explicit `?src=` tag), never from the `source` column. Never set it when the value equals "direct". Do not overwrite a browser that has an `ekuzo_lc` or `ekuzo_origin` of its own? (decide; at minimum only when it has no `ekuzo_bsrc`, as written). |
| A3 | minor | **Stranger kills or poisons a family's restart link and saved answers.** Anyone who knows an email posts `beta-progress` with any new sessionId. PROGRESS_SQL then replaces `answers` and `session_id`; L5 binds the token to the row's current session, so the parent's emailed link goes dead (state `none`, the first screen) and their saved answers are gone. On a finished row it also reopens it (D2) so the family gets a pick-up email whose link restores the attacker's chosen answers (name, age, a 500-char note and fun fact) pre-filled in front of the real parent. D1/D2 accepted the stray email; they did not cover a feature whose value depends on the row surviving. Cost to attacker: one POST per email, 150 an hour per IP. | L5 (session in the HMAC); PROGRESS_SQL `answers = excluded.answers` on session change; open progress endpoint | Cheapest: accept and log as D12, because telling a sibling restart from a stranger needs proof the server cannot get. Reduce harm: (a) restore never returns `note` or `funFact` free text from a row whose session changed in the last day, or never returns free text at all and only the structured fields; (b) the Klaviyo flow keeps the 7-day one-email rule from D1; (c) when a restore returns `none` for a recent row, the first screen is fine, but do not say anything that implies the link was wrong. |
| A4 | minor | **Origin in the emailed link (L7, spec "Existing saves").** "Off production the link uses the request's own origin." If that origin is read from the `Origin`, `Host` or `X-Forwarded-Host` header, a stranger posting progress for a victim's email (curl, no Origin guard applies without an Origin) sets `beta_restart_link` on the victim's Klaviyo profile to `https://evil.example/season1/beta/r/<token>`. The next pick-up email then sends a valid token to the attacker's server and shows the parent a trusted-looking mail pointing off-domain. Closed on production by `keyIsLive()` returning the fixed origin, but a deploy or preview that holds live keys, or a mis-set Stripe key, reopens it. | Spec "Existing saves", L7 | Never derive the origin from a request header. Use the fixed `https://ekuzo.gg` when `keyIsLive()`; otherwise an allowlist (`DEPLOY_PRIME_URL`/`URL` env, or the literal ekuzo.gg and `*.netlify.app` of this site). If the origin is not in the allowlist, write the plain wizard address. Test with a spoofed Host and Origin. |
| A5 | minor | **Bearer token lives in third-party systems for 30 quiet days.** The link is reusable (L6) and sliding (the row's updated_at). It is copied to the Klaviyo profile property, the email body, Klaviyo click-tracking redirects, mail-scanner vendor logs (they fetch every URL, which is the L6 reason), and Netlify's platform access log for the path `/season1/beta/r/<token>` (the app's own logs are covered by L10; the platform's are not). Anyone with that log or an exported profile can read a child's first name, age and answers within the window. M1 says "in a log line"; the platform log cannot be controlled. | L1, L6, L7, M1 | State the residual risk in the spec and shorten it: 14 days absolute from the row's `started_at`, not a sliding 30 from updated_at, and stop returning free-text answers (A3). Keep `beta_restart_link` out of Klaviyo events (profile property only, as written). Add a note to klaviyo-config that profile exports contain live tokens. |
| A6 | minor | **Restore endpoint load.** Per-IP cap fails open after 0.8 s, so a slow or loaded database turns the limiter off exactly when it matters; each call is a limiter write plus a row read. A request with no `x-nf-client-connection-ip` (null material) is not limited in the spec text: `s1br:ip:<hash>` has no value to hash, and `checkLimits` precedent is "no per-IP limit then". An attacker sends any garbage cookie, so every call costs a DB read. | L10; spec Routes item 2 | Do the cheap checks before any database call: cookie present, matches `^[A-Za-z0-9_-]{65}$`, decodes to 16+32 bytes, otherwise return `none` with no limiter and no select. For null IP use a small global bucket (`s1br:global`) instead of nothing. Keep the limiter fail-open only on error, not on slowness of the select itself. |
| A7 | minor (hardening) | **Key derivation shares a primitive with `keyHash`.** `keyHash(v)` is `HMAC(refSecret, lower(trim(v)))` truncated to 22 chars, and the new key is `HMAC(refSecret, "ekuzo:beta-restart:v1")`. If any code path ever exposed `keyHash` of an attacker-chosen string, `keyHash("ekuzo:beta-restart:v1")` would reveal 132 bits of the signing key. Today no `keyHash` output reaches a client (checked: rate-limit keys, `auto-` event ids sent to Klaviyo, a log subject), and the label cannot be a ref code (`signRef` codes are `[A-Za-z0-9]+`), so this is closed now but one change from open. | L5; `rules.ts` keyHash; refcookie.ts mac | Derive with a label no `keyHash` input can equal, e.g. include a `\u0000` or a leading `\n` (keyHash trims, so a trailing/leading whitespace byte is lost; use an interior NUL), and say in a comment that no HMAC output under refSecret may be exposed. Optionally split the key off `refSecret` with HKDF-SHA256 instead. |

## Attack classes checked and found closed

| Class | Result |
|---|---|
| Guess or forge a token | No finding. 16-byte random row id plus a 256-bit MAC; shape check, decode to exact lengths, `timingSafeEqual` after a length check. Implementation note: base64url decoding ignores spare bits, so a few non-canonical strings decode to the same bytes; verify on decoded bytes only (never string-compare or key a cache or deny list on the raw token). |
| Forge a token with a session id the attacker chose | No finding. The message is `v1\|rowId\|sessionId`; `sessionId` is cleaned to `[A-Za-z0-9-]` so it cannot carry the `\|` separator; the row id has a fixed length. |
| Token or key reuse across purposes | No finding beyond A7. The label contains `:` and `-`, so it can never be a signed referral code; the referral cookie MAC input and the derived key never collide. Fallback to `S1_STRIPE_WEBHOOK_SECRET` only happens without a live key. |
| Learn a token through the open progress endpoint | No finding. The endpoint answers `{ok:true}` always and returns nothing from the row. |
| Open redirect | No finding. Location is the constant `/season1/beta/start`; keep it relative (build it from a literal, not from `req.url` or Host). |
| Enumeration through none/done/resume, status or timing | No finding. A response other than `none` needs a valid signature, which needs the token. `none` has one shape for bad signature, unknown row, expiry, superseded session, no cookie and database failure. Timing differences (no select for a malformed cookie, a select otherwise) reveal only that the attacker's own garbage is garbage; see A6 for making the cheap path cheaper. |
| Replay after finish or expiry | No finding. Finished rows return `done` with no data (M3); expiry and session change return `none`. A stranger can reopen a finished row only with a new session, which kills the old token (A3). |
| Cross-site POST to the restore endpoint (CSRF) | No finding. Same Origin guard as /api/season-one blocks browser cross-site POSTs, and the response is unreadable cross-origin anyway. Note the guard must run before the cookie is cleared, or a cross-site page can burn a victim's one-shot cookie by a forced POST; put the 403 first and add a test. |
| Cookie scope | No finding. `ekuzo_brt` is HttpOnly, Secure, Lax, Path `/api/season1-beta`, 30 minutes, cleared on every call; the JS-readable flag carries nothing. Cookie tossing from a sibling subdomain would need subdomain control and is out of scope. |
| Cache and header leakage of the token on the /r/ route | No finding in the spec. 302 with no token in Location, `no-store`, `no-referrer`, noindex, no HTML so no vendor tag. Middleware still runs on the path and may set `ekuzo_origin`, `ekuzo_lc` and `ekuzo_bsrc` from the link's own query string, which is existing behaviour. |
| Flooding the /r/ route | No finding. No database call, a constant 302. |
| A stranger reads a kid's data without a token | No finding for token-less access; A1 is the only route and it needs the victim's participation. |
